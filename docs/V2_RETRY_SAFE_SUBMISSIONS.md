# V2 网络重试与加密待发送草稿

**仅隔离 V2 开发版。** 当前没有上线，也未连接正式 Supabase。

## 已实现的范围

- 数据库迁移 `supabase/migrations/20261019005000_v2_idempotent_submissions.sql` 为文字批注与回复增加可空的 `client_operation_id`，旧记录不用改写。
- V2 前端发送文字批注时调用 `v2_submit_highlight`，发送回复时调用 `v2_submit_reply`。每条编辑中的发送任务使用独立 UUID；失败后保留同一 UUID 和内容，可以重试。
- 服务器用 **书房 + 作者 + 发送 UUID** 唯一约束及事务冲突检测：首次提交返回 `saved`；相同参数重复提交返回 `already_saved`，不会新建第二条记录或第二个创建审计事件。
- 同一 UUID 若被用于不同文字、不同文字范围或私人／共享状态，返回 `conflict`，原数据不被覆盖。隐藏过的回复重试返回 `withdrawn`，不会恢复隐藏内容。陌生人、匿名用户、已关闭书房不能提交。
- 新增待发送内容可通过上一步的本机 AES-GCM 草稿功能**手动加密保存**。备份包括发送 UUID，恢复后仍使用它进行重试；旧版加密笔记（没有 UUID）恢复时分配新的 UUID，不能追溯旧提交的幂等性。
- 用户必须手动确认发送，**不会在联网时自动上传**；私人／共享范围保留并显示于编辑器，避免在后台悄悄公开私人文字。
- 服务端确认 `saved` 或 `already_saved` 后，从编辑器移除已提交内容并尝试清理该位置的本机密文备份。网络异常导致结果未知时保留待发送文字和 UUID。

## 关键限制

- 目前每个本机加密备份作用域（账号 + 书房 + 某一段或某条笔记）只保留**一份草稿**；这不是多条任务同时排队、跨设备自动同步或断网后台上传服务。
- 如果尚未加密备份就刷新／关闭标签页，发送 UUID 可能丢失。即使服务器已经保存了内容，使用新的 UUID 重新发送仍有可能创建第二条记录。**不承诺任意情况下恰好发送一次**。
- 用户在不确定结果之后修改文本、选区或可见性会被视为新发送任务；旧任务可能已经保存在服务器。应先用原 UUID 重试或在阅读列表检查。
- 即使浏览器声称已经联网，服务器也可能不可用。因此不依赖 `navigator.onLine` 自动上传私人内容。
- 直接调用旧的表 INSERT 接口（测试数据库仍向已认证成员开放）不受此新 RPC 的幂等性承诺；旧客户端应逐步迁移。
- 手动本机加密草稿及 UI 尚需真实浏览器、手机、两个账号和独立 Supabase 的端到端测试。数据导出、真正删除和法律保留期限仍未实现。
