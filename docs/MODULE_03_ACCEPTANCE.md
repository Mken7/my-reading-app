# 第 03 一级模块：双人书房、邀请码、审批与撤回

**开发分支代码验收文档。尚未接入独立 Supabase staging 或真实手机验收，禁止视为正式上线。**

## 本模块范围

1. **两人私密房间。** 每间书房只允许一位房主和一位共读伙伴，数据库中 owner/partner 角色由唯一约束保护。未经明确批准的申请人不是成员，无法查看书房内容和内部名册。
2. **六位安全邀请码。** 邀请码有 24 小时有效期，后端只存使用数据库私有随机 pepper 的 SHA-256 摘要。客户端只在当前页面临时展示，可立即隐藏，不写入 localStorage/URL。轮换会使旧码和其待审批申请失效。
3. **房主明确审批。** 申请邀请码不等于入房；房主能允许或拒绝，批准即消耗一次性邀请码并锁定第二席。重放批准和过期/撤销凭证不能再增加任何成员。
4. **申请人可以查看状态和撤回。** 登录账号只可以查看自己最近 20 条申请的 pending/approved/rejected/cancelled 状态。撤回仅允许仍待审批的请求，不会将已经获批的伙伴逐出书房。获得新邀请码后允许重新申请。
5. **撤销邀请码需二次确认。** 房主可撤销未使用的邀请码并拒绝关联的 pending 申请。重复操作不产生新码或双重额度消耗；其他成员及陌生人不允许撤销。
6. **活动成员名册。** 只有活动书房成员能查看至多两个角色与加入时间；陌生账号、申请人、关闭书房均不能获取名册。前端展示 1/2 或 2/2；不公开房内个人邮箱。
7. **登录切换保护。** 跨账号登入、退出时会清除页面保留的验证码、房间列表、审核信息与阅读页面；异步查询携带会话世代标记，防止旧账号迟到响应重新显示于新账号页面。返回窗口时刷新审批信息。
8. **服务端限额。** 每账号每 24 小时最多创建 3 间房、签发 10 次邀请码；每小时最多 5 次邀请码尝试，失败也计数。它不能代替跨账号、网络或设备级风控。

## 实现与验收

- 基础 SQL：supabase/migrations/20261018223000_reading_access_v2.sql、20261018225000_room_invites_v2.sql、20261018230000_v2_issuance_quotas.sql。
- 本轮 SQL：supabase/migrations/20261019011000_v2_room_lifecycle.sql，新增可信 RPC v2_revoke_room_invite、v2_withdraw_room_join、v2_room_roster 和 v2_my_join_requests。
- 界面：app/v2/V2Preview.tsx：申请状态、待审批、两步撤码、一次性码临时展示、房间座位、跨会话缓存失效。
- SQL 回归：tests/sql/reading_room_lifecycle_v2_smoke.sql 以四个独立账号验证申请、撤回、拒绝、再次申请、批准、第三人阻断、匿名与关闭房间权限及数据隔离，继承前面全部迁移/安全测试。
- GitHub CI 要求三个 job 均成功：verify（Node 单测、严格 ESLint、TypeScript 与 Next.js 静态构建）、database-security（临时 PostgreSQL 16）、browser-queue（Chromium 真实浏览器回归）。

## 未完成和设计边界

用户获批后离开房间、替换伙伴、封存数据与真正的账户删除属于第 12 模块；不能把撤回入房申请等同于退出书房。IP/设备级防滥用、平台举报和外部审计属于第 11/13 模块。真实三账号 staging Supabase、iPhone/Android、上线迁移及回滚验收属于第 14 模块。申请状态不提供实时推送；房主撤码与另一端申请恰好同时发生时，极端情况下待审批信息可能短暂显示失效申请，但最终批准仍会核查邀请状态，不会授权过期凭证。

main、生产 Supabase、历史备份分支没有修改；PR #1 维持 draft。本文的“100%”仅针对约定范围内的开发分支代码及自动化验收，不代表实际 App 已发布。
