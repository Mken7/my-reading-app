# 安全、反批量抓取与可维护性方案（设计草案，未上线）

> 状态：仅供后续实施。当前 GitHub Pages 原型 **不具备** 这些服务端控制，不能对公众宣称安全加固已上线。

## 安全边界

浏览器需要显示的书籍文字，获授权的阅读者最终都能接触到；不能彻底禁止复制、截图、浏览器调试或自动化抓取。CSP、robots.txt、禁用右键、前端代码混淆、哈希链和水印均不能替代服务器访问控制。**不可将 service_role / 数据库管理员密钥暴露给浏览器。** 现有 Supabase publishable key 是公开客户端标识，安全性取决于 RLS 等服务端规则。

在上线陌生人广场之前，必须完成独立安全审查与滥用处理流程。不得将原书文字或私人批注发送到第三方爬虫识别服务。

## 接下来分阶段实施

1. **身份与隔离**：Supabase Auth 邮箱登录；成员通过 `auth.uid()` 关联；书籍、批注、回复按用户和两人房间的成员关系强制 RLS；默认拒绝未授权行。旧本地匿名 ID 不视为可信凭据。
2. **最小授权**：用受保护的数据库事务或 Edge Function 负责创建房间、加入邀请、退出/封禁、删改批注。每房最多两名有效成员；邀请码存不可逆摘要、单次使用、有有效期，验证和核准都在服务端。事务锁或唯一约束确保并发时不出现第三位成员。
3. **有边界的阅读**：仅在验证房间权限后分章或分段交付正文；对用户、房间、IP / 设备风险信号做分层频率与流量限额。采用渐进式挑战、人性化限流说明和误判申诉，保持无障碍；不允许通过伪造 CAPTCHA 规避实际权限设计。
4. **反滥用**：暴力尝试邀请码、批量注册、异常分页、异常内容导出均记录必要安全事件并可暂时限制；真实用户允许合法导出自己的笔记。数据保留时间最短化，IP 等风险数据受隐私制度约束。
5. **可验证审计（类区块链而非链上）**：服务端记录 append-only 事件：`seq`, `room_id`, `actor_id`, `action`, `content_digest`, `previous_hash`, `event_hash`, `created_at`，事件按房间有序。计算 `event_hash=SHA-256(规范化结构 + previous_hash)`，服务端周期性地将链头摘要写入独立的只追加存储并签名。严禁把书籍正文和私人笔记明文写入公开审计。哈希链**只提供篡改可发现性，不保证绝对不可篡改**，尤其不能抵御同时掌握数据库、密钥和锚定存储的管理员。
6. **恢复和可维护性**：按认证、房间权限、书籍、批注、阅读器、审计拆分模块；数据库迁移版本化，先在测试项目验证再上线；维护失败回滚预案、最小权限 API、单元/集成/多用户越权测试、持续构建与 lint 门禁。

## 必做验收测试

- 无认证用户不能读书、笔记或成员表；用户 A 不得访问用户 B 书房。
- 同时三人申请加入，仅允许两个合法成员成功；过期/撤销邀请码不可复用。
- 用户撤销共享、被封禁或离房后立刻失去不再拥有的访问权限；Realtime 和 Storage 也同步受限。
- 高频抓取和邀请码猜测会被合理限流，不泄露书籍正文或枚举房间。
- 单条事件被删改会导致链验证失败；轮换签名密钥仍能验证历史锚定记录。
- 断网草稿、笔记可用性和自己的合法导出不因防爬设计而损坏。

## 部署约束

GitHub Pages 是静态托管，不具备保密的服务端 API。下一阶段可利用 Supabase Auth、Postgres RLS 和 Edge Functions，但需先核对其免费额度及实际流量成本并显式防止账单意外增长。现有原型数据结构不能未经迁移检查就直接实施上述权限规则。

## 本阶段不会做的事

- 不部署代币、挖矿、公有链或 NFT。
- 不暗改生产 Supabase 表、RLS、数据或密钥。
- 不使用禁用复制等“表演式防爬”作为安全承诺。
- 不自动删除用户批注或无提示中断合法访问。
