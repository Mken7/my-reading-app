# V2 多条加密待发送草稿队列（仅隔离测试版）

**尚未上线。** 只在 `feat/phase0-foundation-2026-10-18` 的 V2 阅读器代码中实现；不涉及线上 Supabase，不允许擅自合并 `main`。

## 已实现

- 同一账号 + 书房 + 段落/笔记位置下，最多保留 **10 条**独立的待发送文字批注或回复草稿。列表显示数量和匿名序号，正文、可见性、选字位置均不以明文写入浏览器缓存。
- 草稿由用户主动点击「加入加密待发送队列」才写入 `localStorage`。每条操作绑定一个随机 UUID，沿用 Web Crypto AES-GCM、独立随机盐/IV、PBKDF2 派生密钥和口令认证。口令只在本次操作时由用户输入；不储存密码。
- 密文采用账号、书房、记录类型、目标位置及发送 UUID 作关联认证数据（AAD）；索引只存随机 UUID，不含读者姓名、笔记明文或 `private/shared` 状态。相同 UUID 不允许以不同正文或共享范围覆盖旧草稿。
- 用户逐条输入口令进行恢复，然后必须在正常编辑框检查隐私范围和文本，再主动点发送。数据库 `v2_submit_highlight` / `v2_submit_reply` 以相同 UUID 实现幂等重试，避免网络 ACK 丢失导致同一操作重复创建。
- 在线发送得到 `saved` 或 `already_saved` 后，只删除该 UUID 对应的本地加密待发送项；其余未发送记录保持原样。每条支持二次确认后清除。
- 以前只有一份草稿的旧版加密备份仍可手动恢复、覆盖、清除，**不会因为发送了其他队列项目而误删**。这两个存储机制暂时并存。

## 重要限制

- 这是**手动待发送列表**，不是后台自动重试任务，不会在重新联网后发送私人内容。每条必须恢复到编辑框并由用户主动确认发送。
- 仅当前浏览器设备存有密文；不同设备不会自动共享。无痕模式、清理网站数据、忘记口令、磁盘故障都可能使数据永久丢失。
- 最大数量为每个*具体目标位置* 10 条，而非整个账号共 10 条；尚无全站总容量配额与长期淘汰策略。浏览器存储配额满时会报错。
- 索引中保留随机 UUID 及其数量，并非完全隐藏元数据。恶意同源脚本、恶意浏览器扩展、弱口令、操作系统入侵依旧属于风险。
- 多标签页同时添加或删除的本地 `localStorage` 索引没有跨标签事务锁，存在竞态风险。待真实测试后应考虑 IndexedDB 原子事务。
- 如果编辑器中还保有另一条不同的草稿，恢复会拒绝覆盖，以避免静默丢稿。当前只有按每条编号恢复，不提供全房间集中搜索列表。
- 服务端仍需独立 staging Supabase 的双账户真实验收；GitHub CI 仅验证 Node 加密单元测试、React/Next.js 构建与隔离 PostgreSQL 数据权限。
